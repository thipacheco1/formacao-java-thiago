## Conceito essencial

### Comecar pelos requisitos

O modelo físico deve nascer de requisitos verificáveis. Cada regra precisa resultar em uma decisão concreta: tabela, foreign key, unique, check, índice, transação ou responsabilidade da aplicação.

Requisitos centrais:

```text
Cliente e Produto possuem várias Ordens;

Ordem possui Atividades e Pagamentos;

Atividade e Técnico formam muitos para muitos;

mudanças de status geram histórico;

códigos de negócio não repetem;

totais são derivados;

metadados opcionais podem usar JSONB.
```

### Granularidade

Cada linha deve possuir significado único:

```text
Cliente:
cadastro de uma pessoa ou empresa.

Produto:
item do catálogo.

Técnico:
profissional alocável.

Ordem:
solicitação de atendimento.

Atividade:
etapa operacional da Ordem.

Atividade Técnico:
alocação de um Técnico em uma Atividade.

Pagamento:
parcela financeira.

Histórico:
estado inicial ou transição da Ordem.
```

A granularidade correta evita duplicação de valores e relatórios ambíguos.

### Chave tecnica e chave de negocio

As entidades usarão `id bigint identity` como chave técnica e códigos, matrícula ou documento como chaves de negócio protegidas por `UNIQUE`. IDs estabilizam relacionamentos; chaves de negócio evitam duplicidades relevantes. Documento não será primary key porque possui regras e formatos próprios.

### Identity

As tabelas usarão `GENERATED BY DEFAULT AS IDENTITY`. Isso permite IDs explícitos no seed e geração automática nas inserções normais. Depois do seed, `setval` deve posicionar cada sequence acima do maior ID utilizado.

### Tipos fisicos

O projeto usará `bigint` para identidades, `text` para códigos e descrições, `numeric(12, 2)` para dinheiro, `timestamptz` para instantes, `date` para dias planejados, `boolean` para estados binários, `integer` para versão e `jsonb` para metadados opcionais. Dinheiro e datas não serão armazenados como ponto flutuante ou texto.

### Valores financeiros

Produto, Ordem, Atividade e Pagamento possuem valores com significados diferentes. O preço atual do Produto não substitui o valor previsto da Ordem. Totais de mão de obra, pago, pendente e saldo serão derivados na aula 308, evitando colunas redundantes que poderiam divergir.

### Status como texto controlado

O projeto usará `text` com `CHECK` para status da Ordem, Atividade e Pagamento. A solução mantém o contrato visível e pode evoluir para tabelas de referência quando os status adquirirem configuração ou atributos próprios.

### Coerencia temporal

Checks locais impedirão `atualizado_em` anterior a `criado_em`, conclusão anterior à abertura, fim de Atividade anterior ao início e Pagamento marcado como pago sem data e meio de pagamento.

### Ordem concluida

Uma Ordem `CONCLUIDA` exige `concluida_em` preenchido e não anterior à abertura. Outros status mantêm essa coluna nula. Cancelamento possui semântica própria e será identificado pelo histórico.

### Versao otimista

A coluna `versao` começa em zero e não pode ser negativa. Uma camada Java futura poderá atualizar usando `WHERE id = ? AND versao = ?`, incrementando o valor para detectar alterações concorrentes.

### Muitos para muitos

Atividade e Técnico usam a tabela associativa `atividade_tecnico`, cuja primary key é `(atividade_id, tecnico_id)`. A relação guarda `papel`, `horas_previstas` e `alocado_em`, atributos que não pertencem isoladamente a nenhuma das entidades.

### Historico de status

A Ordem mantém o estado atual; `ordem_status_historico` registra estado inicial e transições com data, origem, ator e motivo. O histórico é tratado como imutável. A aplicação deverá atualizar Ordem e histórico na mesma transação e validar que o último evento corresponde ao estado atual.

### Politica de exclusao

As foreign keys usarão `ON DELETE RESTRICT` para impedir que a exclusão de Cliente, Ordem ou Técnico remova silenciosamente registros operacionais. Inativação e mudança de status são preferíveis à exclusão física.

### Metadados JSONB

`ordem_servico.metadados` aceitará somente objeto JSONB e guardará canal, correlation ID, tags ou dados opcionais. Identidade, status, valores, Atividades e Pagamentos permanecerão relacionais. Nenhum GIN será criado sem consulta essencial comprovada.

### Indices orientados por acesso

Os índices atenderão Ordens por Cliente ou status, Atividades por Ordem, alocações por Técnico, Pagamentos por Ordem, pendências por vencimento e histórico cronológico. Primary keys e uniques já criam índices; estruturas duplicadas não serão adicionadas.

### Indice parcial

Pagamentos pendentes serão consultados frequentemente por vencimento.

Será criado:

```sql
CREATE INDEX ...
ON pagamento (
    vencimento,
    id
)
WHERE status = 'PENDENTE';
```

O índice contém somente linhas pendentes.

Ele não ajuda uma consulta que ignora ou contradiz o predicado.

---

### Regras que o banco nao garante sozinho

Invariantes entre várias linhas continuam sob responsabilidade transacional da aplicação, por exemplo: Ordem com ao menos uma Atividade, soma de Pagamentos compatível com o valor previsto, último histórico igual ao status atual e ausência de conflito de agenda entre Técnicos. O projeto documentará essas limitações.

### Scripts versionados

A cadeia terá V1 para entidades base, V2 para entidades operacionais, V3 para índices e V4 para seed. Depois de aplicados, os arquivos são imutáveis; correções futuras devem criar V5 ou versão posterior.

### Seed minimo

O seed incluirá cenários concluído, em atendimento, aberto, agendado e cancelado; Cliente sem Ordem; Técnico sem alocação; Atividade com dois Técnicos; Pagamentos pagos e pendentes; Ordem sem Pagamento; e históricos com uma ou várias transições. Assim, o modelo será validado além do caminho feliz.

CREATE TABLE projeto_os_final.ordem_servico (
    id bigint GENERATED BY DEFAULT AS IDENTITY,

        DEFAULT CURRENT_TIMESTAMP,

    valor_previsto numeric(12, 2) NOT NULL
        DEFAULT 0,
    versao integer NOT NULL DEFAULT 0,
    metadados jsonb NOT NULL
        DEFAULT '{}'::jsonb,
    criado_em timestamptz NOT NULL
        DEFAULT CURRENT_TIMESTAMP,

        DEFAULT CURRENT_TIMESTAMP,

        PRIMARY KEY (id),

    CONSTRAINT uq_pof_ordem_codigo

        CHECK (btrim(codigo) <> ''),

    CONSTRAINT ck_pof_ordem_status
        CHECK (
            status IN (
                'ABERTA',
                'AGENDADA',
                'EM_ATENDIMENTO',
                'CONCLUIDA',
                'CANCELADA'
            )
        ),

    CONSTRAINT ck_pof_ordem_prioridade
        CHECK (
            prioridade IN (
                'BAIXA',
                'NORMAL',

                'CRITICA'
            )
        ),

    CONSTRAINT ck_pof_ordem_descricao
        CHECK (
            btrim(descricao_problema) <> ''
        ),

    CONSTRAINT ck_pof_ordem_valor
        CHECK (valor_previsto >= 0),

    CONSTRAINT ck_pof_ordem_versao
        CHECK (versao >= 0),

    CONSTRAINT ck_pof_ordem_metadados
        CHECK (
            jsonb_typeof(metadados)

            )

        CHECK (
            atualizado_em >= criado_em
        )

            )
        )

            )
        ),

    CONSTRAINT ck_pof_historico_transicao

            )
        ),

```sql
SELECT
    cliente.id,
    cliente.codigo,
    count(ordem.id) AS quantidade_ordens
FROM projeto_os_final.cliente AS cliente
LEFT JOIN projeto_os_final.ordem_servico AS ordem
    ON ordem.cliente_id = cliente.id
GROUP BY
    cliente.id,
    cliente.codigo
ORDER BY cliente.id;

SELECT
    ordem.id,
    ordem.codigo,
    count(
        DISTINCT atividade.id
    ) AS atividades,
    count(
        DISTINCT pagamento.id
    ) AS pagamentos,
    count(
        DISTINCT historico.id
    ) AS historicos
FROM projeto_os_final.ordem_servico AS ordem
LEFT JOIN projeto_os_final.atividade AS atividade
    ON atividade.ordem_servico_id = ordem.id
LEFT JOIN projeto_os_final.pagamento AS pagamento
    ON pagamento.ordem_servico_id = ordem.id
LEFT JOIN projeto_os_final.ordem_status_historico AS historico
    ON historico.ordem_servico_id = ordem.id
GROUP BY
    ordem.id,
    ordem.codigo
ORDER BY ordem.id;

SELECT
    atividade.id,
    atividade.codigo,
    count(alocacao.tecnico_id)
        AS tecnicos
FROM projeto_os_final.atividade AS atividade
LEFT JOIN projeto_os_final.atividade_tecnico AS alocacao
    ON alocacao.atividade_id = atividade.id
GROUP BY
    atividade.id,
    atividade.codigo
ORDER BY atividade.id;
```

O `COUNT DISTINCT` evita multiplicação entre as três relações filhas. Na aula 308, somas usarão pré-agregação.

## Entendendo o que foi feito

O modelo cresceu sem perder normalização. Técnico tornou-se entidade e a relação com Atividade recebeu tabela associativa. Estado atual e histórico foram separados, totals permaneceram derivados e o JSONB ficou limitado a extensões opcionais.

As migrations permitem reconstrução ordenada, o seed cobre cenários variados e os índices iniciais correspondem a consultas previstas. A aula 308 poderá criar relatórios sem alterar o núcleo físico.

## Erros comuns importantes

### Guardar Tecnicos em array

Isso elimina foreign keys e atributos da alocação. Use tabela associativa.

### Armazenar totais na Ordem

Totais podem divergir dos filhos. Calcule por consulta.

### Usar CASCADE indiscriminadamente

Exclusões podem apagar histórico. Defina a política por relacionamento.

### Criar indice duplicado

Primary keys e uniques já possuem índices.

### Limpar o schema ao final

A aula 308 depende de `projeto_os_final`.

Preencha os dados coerentes.

Existem objetos dependentes. A proteção sem `CASCADE` está funcionando.
